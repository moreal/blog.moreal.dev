# 저장소 리팩터링

한 번 실행에 `src` 전체를 리팩터링한다. 동작은 그대로 두고 읽기 쉽게 바꾼 뒤 main에 커밋 하나를 남기고, Codex 리뷰에서 고칠 지적이 없어질 때까지 다듬는다. 이전 실행의 기억은 없다. git 기록이 상태의 전부다.

## 원칙

- **동작을 바꾸지 않는다.** 라우트 응답의 형태, URL, 빌드된 HTML은 그대로여야 한다. 버그를 발견하면 고치지 말고 보고에 적는다.
- **주석 대신 코드로 말한다.** 주석이 설명하던 내용은 이름, 타입, 함수 분리, 테스트 이름으로 옮기고 주석을 지운다. 어디로도 옮길 수 없는 제약만 주석으로 남긴다.
- **사용자의 작업을 건드리지 않는다.** 이 작업 트리에서는 사용자가 원고를 쓰고 있다. `git status --porcelain -- <파일>`의 출력이 비어 있지 않은 파일은 수정 중이므로 읽기만 한다. `git stash`, `git reset`, `git checkout .`, `git add -A`, `git add .`은 쓰지 않는다.

## 무엇을 고치나

| 보이는 것 | 고치는 방법 |
|---|---|
| 라우트·컴포넌트 안에 판단 로직이 섞여 있음 | 순수 함수로 떼어 모듈로 옮기고 테스트를 붙인다 |
| 같은 코드가 두 곳 이상에 있음 | 한 곳으로 모은다 |
| 한 글자·축약 이름, 하는 일을 말하지 않는 이름 | 뜻이 드러나는 이름으로 바꾼다 |
| 한 함수가 여러 일을 함 | 이름 붙은 작은 함수로 나눈다 |
| 설명 주석이 있어야 읽히는 코드 | 이름과 구조로 옮기고 주석을 지운다 |
| 참조가 없는 export·함수·CSS 규칙 | grep으로 참조가 없음을 확인하고 지운다 |

모듈 경계:

- `src/admin/lib/`는 `node:fs`에 닿는 서버 전용 코드다. `src/admin/ui/`에서 import하지 않는다.
- 서버와 브라우저가 함께 쓰는 코드는 `src/admin/shared/`에 둔다.
- `src/admin/lib/types.ts`에는 타입만 둔다. ui가 import하므로 런타임 값이 들어가면 node 코드가 브라우저 번들에 끌려간다.
- 사이트 쪽 로직은 `src/lib/`에 두고 `src/pages/`와 `src/components/`는 얇게 유지한다.
- 테스트는 대상 옆의 `*.test.ts`에 `node:test`와 `node:assert/strict`로 쓴다.

하지 않는 것: 의존성 추가, 포매팅만 바꾸기, 같은 수준의 스타일끼리 바꾸기, 기능 추가, 문자열째 HTML에 들어가는 코드(인라인 스크립트 등)의 내용 바꾸기.

## 절차

스크립트 경로는 `S=.claude/skills/refactor`로 줄여 쓴다.

1. **기준선.** `$S/build-diff.sh snapshot`, `yarn test`, `yarn run check`를 실행해 통과를 확인하고, check 요약 줄의 경고·힌트 수를 기억한다.
2. **훑어보기.** `src` 전체를 읽고 위 표에 해당하는 곳을 목록으로 만든다. 여러 파일에 걸친 것(중복, 경계를 넘는 로직)을 먼저 본다. 수정 중인 파일은 목록에서 뺀다. 고칠 것이 없으면 7단계로 간다.
3. **동작 고정.** 옮기거나 바꿀 로직에 테스트가 없으면 지금 코드에 대한 테스트를 먼저 쓰고 통과시킨다. 테스트할 수 없게 묶여 있는 로직은 export하거나 경로 같은 고정값을 인자로 받게 하는 정도까지만 먼저 바꾸고 테스트를 쓴다.
4. **리팩터링.** 목록을 하나씩 처리하고, 하나를 마칠 때마다 `yarn test`로 깨진 곳을 바로 찾는다. 빌드 결과에 나타나지 않는 CMS 라우트를 바꿨으면 dev 서버를 띄워 바꾸기 전과 응답을 비교하고, 비교가 끝나면 서버를 끈다.
5. **검증.** 셋 다 통과해야 한다.
   - `yarn test`
   - `yarn run check`: 오류 0개, 경고·힌트가 기준선보다 늘지 않음
   - `$S/build-diff.sh compare`: `IDENTICAL` 또는 `BUNDLE-ONLY`. `DIFFERS`일 때 달라진 페이지가 모두 그 사이 수정된 원고(`git status`의 `20xx/` 파일)에서 나온 것이면 통과로 본다.

   통과하지 못하는 변경은 원인을 고친다. 고칠 수 없으면 그 변경만 되돌리고 보고에 적는다.
6. **커밋과 Codex 리뷰.**
   1. 바꾼 파일을 경로로 하나씩 `git add`하고 커밋한다. 메시지는 영어로 쓴다. 첫 줄은 무엇을 했는지 명령형으로 72자 이내, 본문은 주제별로 무엇을 어떻게 왜 바꿨는지 쓴다. `BUNDLE-ONLY`였으면 본문에 "Client bundle changed."를 적는다. 메시지 끝에는 `Co-Authored-By: <자신의 모델 이름, 예: Claude Opus 5> <noreply@anthropic.com>`을 붙인다.
   2. `$S/codex-review.sh`로 이 커밋만 리뷰받는다. 커밋 전 작업 트리를 리뷰하면 추적되지 않는 원고까지 Codex로 보내게 되므로, 커밋 전에 리뷰하거나 `--scope working-tree`를 쓰지 않는다.
   3. 고칠 지적이 있으면 고치고 5단계 검증을 다시 통과시킨다. 빌드 비교는 1단계의 기준선과 한다. 바꾼 파일을 경로로 `git add`하고 `git commit --amend`로 같은 커밋에 합치며, 바뀐 내용에 맞게 메시지도 고친다. amend는 이번 실행에서 만든 커밋에만 쓴다. 그리고 2로 돌아간다. 횟수 제한은 없다.

   다음 지적은 고치지 않고 사유만 남기며, 남은 지적으로 치지 않는다.
   - 동작을 바꾸라는 지적: 버그로 보고한다.
   - 설명 주석을 달라는 지적
   - 사용자가 수정 중인 파일에 대한 지적: 리뷰는 작업 트리의 추적 파일 변경도 함께 본다.

   스크립트가 0이 아닌 코드로 끝나 리뷰가 실행되지 않으면, 커밋은 그대로 두고 오류를 보고에 적는다.
7. **보고.** 아래를 짧게 알린다.
   - 커밋 해시와 주제별 변경 요약
   - Codex 리뷰가 몇 번째에 통과했는지와 사유만 남긴 지적
   - 발견했지만 고치지 않은 버그
   - 되돌린 변경과 수정 중이라 건너뛴 파일
